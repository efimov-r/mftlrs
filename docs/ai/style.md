# Стиль

Договорённости о стиле кода и текстов в этом проекте. Они важнее общих привычек агента.

## Какой стиль где

- **Существующие файлы upstream** — в стиле окружающего кода: комментарии и KDoc на английском, перенос строк около 100 символов, заголовок с копирайтом не трогать, имена и идиомы — как в соседних файлах. Цель — маленький diff и меньше конфликтов при слиянии upstream.
- **Новые файлы mftlrs** — правила ниже.
- Архитектурные приёмы — как в проекте: ViewModel + LiveData для состояния экрана, `java8.nio` для файлов, ViewBinding. Новые асинхронные вещи можно писать на корутинах и Flow — upstream сам так делает в новом коде (`storage/LanSmbServerListLiveData.kt`).

## Заголовки файлов и авторство

Требование GPLv3: сохранить копирайт автора и пометить изменённые файлы с датой — чтобы ошибки форка не приписывали автору upstream ([decisions.md](decisions.md)).

- **Файл upstream, который меняем:** копирайт Hai Zhang не трогать; в заголовок — строка `Modified for mftlrs, <год>.` сразу после `All Rights Reserved.` (в XML — с префиксом `  ~ `, в Kotlin/Gradle — ` * `). Если строка уже есть — не дублировать. Сами правки — с комментарием `mftlrs:`.
- **Новый файл mftlrs:**
  ```
  /*
   * Copyright (c) 2026 mftlrs contributors
   * SPDX-License-Identifier: GPL-3.0-or-later
   */
  ```
  В XML — то же в `<!-- -->`.
- Правообладатель форка везде — `mftlrs contributors`, без имён.

## Код (Kotlin, новые файлы)

### Форматирование

- Отступ — 4 пробела, без табов; продолжение выражения — ещё +4.
- Переводы строк — LF.
- Длина строки — до ~120 символов, жёсткого предела нет.
- Скобки — K&R: `{` в конце строки, `} else {` на одной строке.
- Пробелы: `if (`, `for (`, `while (`; лямбда `{ x -> }`; тип возврата `fun x(): Boolean`.
- Однострочные проверки без скобок: `if (x == null) return`, `?: return`.
- Многострочные параметры и аргументы — каждый на своей строке, `)` — на отдельной; в вызовах — trailing comma и именованные аргументы.
- Цепочки вызовов — каждый вызов с новой строки, отступ +4.

### Пустые строки

- Между функциями — одна пустая строка.
- Внутри функции пустой строкой отделяются логические шаги: подготовка, вызов, обработка результата, лог.
- Группы полей и констант отделяются пустой строкой.

### Комментарии

- Только там, где без них непонятно; много не писать.
- В конце строки с кодом; строк, где только комментарий, избегать.
- Коротко, на русском.

### Имена

- Классы и объекты — PascalCase, функции и переменные — camelCase, константы — `private const val UPPER_SNAKE`.
- Короткие имена в лямбдах и циклах допустимы: `it`, `s`, `f`.
- Префикс `_` у приватных backing-свойств: `_state` / `state`.
- Суффиксы ролей: `*Util` — `object` с утилитами, `*Holder` — синглтон-держатель клиента, `*UseCase` — класс с `suspend operator fun invoke`, `*Impl` — реализация интерфейса, `*Catching` — функция, которая сама ловит исключения.
- В остальном — имена и структуру брать из соседних файлов проекта.

### Файлы

- Один класс на файл, имя файла = имя класса.
- Исключения: маленькие `data class` рядом с использованием; `data class XUiState` — в конце файла ViewModel; набор верхнеуровневых функций по теме — в одном файле.
- `package` — как у соседних файлов той же папки.

### Идиомы

- Корутины вместо потоков: `withContext(Dispatchers.IO)`, `async { } … awaitAll()`, `Mutex().withLock` вместо `synchronized`.
- Null: `?.let { x -> }`, `?: return`, `?: run { …; return null }`.
- Явные метки возврата: `return@launch`, `return@async`.
- Функции-выражения: `fun f() = …`.
- Ошибки: `runCatching { }.fold(…)` или `.getOrElse { }`.
- Лог на каждом значимом шаге, коротко.

## Тексты

- **Сообщения коммитов** — как в `git log` upstream: `<Тип>: <что сделано>` на английском, типы `Feat`, `Fix`, `Build`. Без `Co-Authored-By`.
- **Строки интерфейса** — в `res/values/strings.xml` (английский) и сразу, в том же изменении, во все 22 локали `res/values-*` (перевод — агент). Комментарий `<!-- mftlrs: … -->` над блоком — как в `values/`. Пробелы в переводах upstream не заполнять: их файлы перегенерирует Transifex, будут конфликты при слиянии. Формы `plurals` — по правилам языка (ru, uk, pl, cs, ro — больше двух форм). RTL выключен (`supportsRtl="false"`), зеркальную раскладку не проверять.
- **Документация** (`AGENTS.md`, `docs/`) — на русском, без личной информации (`AGENTS.md`, «Правила работы»).
- **Таблицы в документации:** одна таблица, без дробления на сводную и подробную. Превью Markdown в IDE сжимает узкие колонки до одного символа, поэтому связанные числа объединять в одну колонку (`4300 (7,9%)`), первую колонку держать короткой, длинные перечни (например, библиотеки) — числом в таблице и списком под ней.
