## 2026-11-15 — UI не держим совместимым с upstream

- **Статус:** принято
- **Контекст:** правило «в файлах upstream менять минимум» мешает чистить интерфейс (RTL, боковая панель, старые темы), а интерфейс всё равно будет переписан (решение ниже, «Главный экран на Compose»)
- **Решение:** в UI-коде и ресурсах (Activity, Fragment, диалоги, разметка, свои View в `ui/`, адаптеры, стили, drawable) совместимость с upstream не сохраняем: правим, упрощаем, удаляем свободно. Правило минимума правок остаётся для логики: `provider/`, `filejob/`, `settings/`, модели, `util/` вне View-расширений
- **Почему:** весь UI рано или поздно переписываем на Compose — усилия на совместимость Views с upstream пропадут вместе с ними
- **Альтернативы:** держать минимум правок и в UI — отказались: тащим лишний код до переписывания ради слияний, которые потом всё равно потеряют смысл
- **Последствия:** правки upstream в UI-файлах при слиянии чаще конфликтуют — по умолчанию брать нашу версию, полезные исправления upstream переносить вручную ([upstream.md](upstream.md))

## 2026-11-15 — Переводы: 22 языка, без RTL

- **Статус:** принято
- **Контекст:** 33 локали от upstream (Transifex); новые строки форка были только в en и ru, в остальных локалях — английский. Своих переводчиков у форка нет. RTL-языки (арабский, персидский, иврит) требуют проверять зеркальную раскладку каждого нового экрана
- **Решение:** удалить 11 локалей — баскский, галисийский, исландский, литовский, каталанский, норвежский, датский, финский, арабский, персидский, иврит (`values-eu`, `-gl`, `-is`, `-lt`, `-ca`, `-nb`, `-da`, `-fi`, `-ar`, `-fa`, `-iw`); в `AndroidManifest.xml` — `supportsRtl="false"`; код учёта направления письма удалён: `ui/AutoMirrorDrawable.kt`, `isLayoutDirectionRtl`, `layoutDirectionCompat`, ветки RTL в `BreadcrumbLayout`, `NavigationRecyclerView`, `Persistent*Layout`, `slideIn`/`slideOut`, `autoMirrored` у двух иконок (`start`/`end` в разметке и `GravityCompat.START` оставлены — при LTR это левый и правый край). Новые строки форка агент переводит сразу во все 22 оставшиеся локали ([style.md](style.md), «Тексты»); пробелы в переводах upstream не заполнять
- **Почему:** у удалённых не-RTL языков меньше 10 млн интернет-пользователей, носители обычно знают английский или соседний оставленный язык (Android берёт следующий язык из списка пользователя); eu переведён на ~54%, у gl, is машинный перевод агента слабее. RTL — выбор владельца: не проверять зеркальную раскладку новых экранов на Compose
- **Альтернативы:** оставить RTL и проверять через «Писать справа налево» в настройках разработчика — отказались, хотя это ~316 млн потенциальных пользователей (арабский ~237, персидский ~70, иврит ~9); удалить только переводы без `supportsRtl="false"` — бессмысленно: раскладка зеркалится по языку системы, а не по наличию перевода
- **Последствия:** при слиянии с upstream — конфликты «удалено у нас» в 11 папках и в строке `supportsRtl` манифеста ([gotchas.md](gotchas.md)). В системе с RTL-языком интерфейс на английском, раскладка слева направо; имена файлов на арабском и иврите отображаются как обычно — направление текста внутри строки определяет система

## 2026-11-15 — Главный экран на Compose; `filelist` расходится с upstream

- **Статус:** предложено
- **Контекст:** главный экран — `FileListFragment` (~1750 строк) на Views; впереди редизайн без боковой панели. Хочется писать новый интерфейс на Compose. Правило проекта — в файлах upstream менять минимум
- **Решение:** переписывать главный экран на Compose по этапам внутри существующего фрагмента ([todo.md](todo.md), «Главный экран на Compose»); новый код — в новых файлах; ViewModel на LiveData оставить; диалоги остаются `DialogFragment`. Проверка после каждого этапа — ручной чек-лист [file-list-checklist.md](file-list-checklist.md), unit-тесты — на логику, вынесенную из фрагмента
- **Почему:** редизайн всё равно переделывает этот экран; поэтапно приложение остаётся рабочим. UI-тесты на старый экран (Espresso) после переписывания пришлось бы выбросить, сквозные (UI Automator) для одного разработчика дороги и нестабильны
- **Альтернативы:** редизайн на Views — без новой зависимости, но верстать новый экран на Views дольше; переписать экран целиком за раз — долго без рабочей сборки, ошибки не локализовать
- **Последствия:** правки upstream в `FileListFragment`, `FileListAdapter`, `BreadcrumbLayout`, разметке `file_list_*` и `navigation/` перестанут вливаться автоматически — переносить вручную или отбрасывать ([upstream.md](upstream.md)). APK вырастет на несколько МБ за счёт Compose

## 2026-11-15 — Две фиксированные темы, палитра mftlrs

- **Статус:** принято
- **Контекст:** у upstream — Material Design 2 с выбором из ~20 цветов, Material Design 3 с цветами из обоев (Material You), переключатель между ними и «чёрный фон» тёмной темы
- **Решение:** только Material 3, две темы — светлая и тёмная с фиксированной палитрой (бирюзово-зелёный акцент, сине-серые поверхности, оранжевый третий цвет; все роли заданы явно). Выбор между ними — «Ночной режим». Пункты «Цвет темы», «Material Design 3», «Ночная тема» убраны из настроек
- **Почему:** один продуманный вид; цвета из обоев и выбор цвета владельцу не нужны
- **Альтернативы:** оставить цвета из обоев переключателем; оставить MD2 с выбором цвета — отказались
- **Последствия:** код и ресурсы MD2, выбора цвета, `.Black` и цветов из обоев удалены полностью (решение владельца — «лишнее удалить»), манифест ссылается прямо на темы Material 3. При слиянии с upstream возможны конфликты в удалённых файлах и в `FileListAdapter`, `ThemedSpeedDialView`, `ThemedSwipeRefreshLayout`, `Settings.kt`, `SettingsActivity`, `AppActivity`, строках всех локалей — правки upstream в удалённом коде отбрасывать ([gotchas.md](gotchas.md))

## 2026-11-15 — `minSdk` 26, без запечённых PNG-иконок

- **Статус:** принято
- **Контекст:** нужно перекрасить иконку приложения и ярлыков. При `minSdk` 23 для Android 6–7.1 нужны PNG с «запечённым» цветом (25 файлов в `res/`), их пришлось бы выгружать заново через Inkscape при каждой смене цвета
- **Решение:** `minSdk` 26 (Android 8.0) — адаптивные иконки работают везде; PNG `mipmap-*/launcher_icon.png` и `*_shortcut_icon.png` и их выгрузки в `art/` удалены, скрипты `art/*-png.sh` урезаны. Цвет иконок — ресурс в `colors.xml`
- **Почему:** смена цвета — одна строка; Android 6–7.1 — единицы процентов устройств
- **Альтернативы:** оставить 23 и выгружать PNG — лишняя работа при каждой смене цвета; поднять выше (29–30) — отдельное решение, затронет работу с хранилищем
- **Последствия:** строка `minSdk` в `app/build.gradle` отличается от upstream — возможен конфликт при слиянии. Код с проверками версий ниже 26 не чистим (lint `ObsoleteSdkInt` — только предупреждения), папку `mipmap-anydpi-v26` не переименовываем

## 2026-11-15 — Атрибуция: «основано на Material Files», связь — только с форком

- **Статус:** принято
- **Контекст:** нужно сохранить указание на автора оригинала, но так, чтобы ошибки форка не приписывали ему и пользователи не шли с проблемами в upstream. GPLv3 требует сохранить копирайт и пометить изменённую версию (раздел 5a), показать правовую информацию в интерфейсе (5d)
- **Решение:**
  - экран «О программе»: раздел «Автор» (имя, GitHub, Twitter автора upstream) заменён пунктом «Основано на: Material Files — Hai Zhang» со ссылкой на upstream; «Посмотреть на GitHub» и политика конфиденциальности ведут на форк; в «Лицензиях» первой — запись mftlrs, запись Material Files сохранена
  - README, PRIVACY.md, SECURITY.md, описания fastlane переписаны: форк, не связан с upstream, проблемы — в issues форка; в README лицензия с двумя копирайтами
  - копирайты upstream в файлах не трогаются; изменённые файлы — строка `Modified for mftlrs, <год>.`; новые — `mftlrs contributors` + SPDX ([style.md](style.md))
  - удалены материалы только upstream: `README_zh-CN.md`, `.github/pull_request_template.md`, `fastlane/.../zh-CN/`, changelogs upstream
- **Почему:** атрибуция сохранена там, где её требует GPL и где она по смыслу (О программе, Лицензии, README, описание в магазине); все каналы обратной связи — к форку
- **Альтернативы:** оставить раздел «Автор» как есть — выглядит, будто Hai Zhang автор mftlrs; убрать упоминание совсем — нарушает GPL и некрасиво
- **Последствия:** правообладатель форка — `mftlrs contributors`, без личных данных; строки `about_author_*` и иконки person/twitter не используются, но оставлены в ресурсах — меньше конфликтов с upstream

## 2026-11-15 — `applicationId` — `io.github.<логин GitHub>.mftlrs`

- **Статус:** принято
- **Контекст:** нужен свой `applicationId`, гарантированно уникальный; один префикс для всех приложений владельца. С 2026 года Google требует регистрировать имя пакета (Android developer verification): занятое имя — дополнительная проверка
- **Решение:** префикс по адресу GitHub Pages аккаунта владельца (`<логин>.github.io` → `io.github.<логин>`, дефис в логине → `_`). Значение — в `app/build.gradle`. `namespace` и Kotlin-пакет остаются upstream
- **Почему:** адрес на `github.io` есть только у владельца аккаунта — уникальность гарантирована, бесплатно
- **Альтернативы:** свой домен — тоже уникален, но платно; придуманный префикс (`com.<слово>`) — домен чужой, уникальность не гарантирована
- **Последствия:** до первой публикации (Google Play, F-Droid, регистрация в Android Developer Console) ID можно менять. После — нельзя: новый ID = другое приложение, установленные копии не обновятся, настройки не перенесутся

## 2026-11-15 — Стиль: в файлах upstream — стиль upstream, в новых — свой

- **Статус:** предложено
- **Контекст:** у upstream свой стиль (английские комментарии и KDoc, перенос около 100 символов, заголовок с копирайтом, перевод строки в конце файла), у владельца — свой ([style.md](style.md))
- **Решение:** правки в существующих файлах upstream — в стиле окружающего кода; новые файлы mftlrs — в стиле владельца
- **Почему:** меньше конфликтов при слиянии обновлений upstream и единообразие внутри файла
- **Альтернативы:** переформатировать всё под стиль владельца — огромный diff и конфликты при каждом обновлении upstream

## 2026-11-15 — Отчёты о падениях: ACRA вместо Firebase, без своего бэкенда

- **Статус:** принято частично: Firebase вырезан 2026-11-15, ACRA ещё не подключена
- **Контекст:** в MaterialFiles встроены Firebase Analytics и Crashlytics — отчёты уходят в Google. В форке они и так не запустятся (проверка пакета и подписи upstream), но остаются в APK. Была идея написать свой сервер для отчётов
- **Решение:** вырезать Firebase. Этап 1 — [ACRA](https://github.com/ACRA/acra) (Apache-2.0) без сервера: при падении диалог «Отправить отчёт?», отправка письмом или через «Поделиться». Этап 2, когда появятся пользователи, — сервер [Acrarium](https://github.com/F43nd1r/Acrarium) (Apache-2.0) в Docker, ACRA переключается на HTTP-отправку
- **Почему:** свой бэкенд — недели работы не по теме проекта: деобфускация стектрейсов R8 по `mapping.txt` каждой версии, группировка одинаковых падений, поиск, надёжная отправка с клиента. Acrarium всё это уже умеет
- **Альтернативы:** свой бэкенд — см. выше; Sentry self-hosted — тяжёлый, рекомендуют 16 ГБ RAM; GlitchTip, Bugsink — Sentry-совместимые, лёгкие, у Bugsink нестандартная лицензия
- **Последствия:** отправка только с согласия пользователя (иначе F-Droid ставит пометку «Tracking»); в отчётах не собирать пути и имена файлов; для Google Play нужна политика конфиденциальности. На этапе 2 адрес сервера в приложении — доменное имя, не IP: при переезде сервера меняется только DNS-запись

## 2026-11-14 — Форк на GitHub, а не копия; Kotlin-пакет не переименовывать

- **Статус:** форк — принято; пакет — рекомендация, не решение
- **Контекст:** код можно взять форком на GitHub (видна связь «forked from») или клоном в новый репозиторий без связи; по GPLv3 допустимы оба
- **Решение:** форк на GitHub. Обновления upstream подтягиваются из удалённого `upstream`. Kotlin-пакет `me.zhanghai.android.files` не переименовывать, менять только `applicationId`
- **Почему:** сразу видно, чей это код; кнопка «Sync fork». Переименование пакета задело бы все 700+ файлов и превратило бы каждое обновление upstream в конфликт; к тому же имена классов записаны в сохранённых настройках ([gotchas.md](gotchas.md))
- **Альтернативы:** копия в новый репозиторий — без видимой связи с оригиналом
- **Последствия:** форк остаётся публичным, сделать его приватным нельзя. Upstream PR не принимает, так что «PR автору» — не вариант

## 2026-11-14 — Основа — форк MaterialFiles

- **Статус:** принято
- **Контекст:** нужен файловый менеджер для Android, который можно дорабатывать как хочется; форкнуть по лицензии можно только open-source менеджеры
- **Решение:** форкнуть [MaterialFiles](https://github.com/zhanghai/MaterialFiles)
- **Почему:** почти чистый Kotlin; бэкенд на провайдерах NIO2 — новые источники файлов добавляются без переделки UI; уже есть FTP, SFTP, SMB, WebDAV и root; проект жив
- **Альтернативы:** Amaze — больше готовых функций, но старый связанный код (Java и Kotlin); Fossify File Manager — без сети, тянет общую библиотеку Commons; OI File Manager (Apache-2.0) — заброшен. Сравнение — [upstream.md](upstream.md)
- **Последствия:** проект под GPLv3: при распространении исходники открыты; нужны своё название, иконка и `applicationId`
